# Rhinestone Debug Issues

## Context

- App: `apps/manager`
- Network: `customSepolia`
- Smart account provider: Rhinestone
- External wallet path: MetaMask EOA
- Embedded wallet path: Para embedded wallet

Observed behavior:

- Para embedded wallet path works.
- External MetaMask EOA path hits two separate failures.

## Issue 1: HCA Registration Fails On External EOA Connect

### Sequence on MetaMask connect

1. `RhinestoneSDK.createAccount()`
2. `rhinestoneAccount.isDeployed(customSepolia)`
3. If not deployed: `rhinestoneAccount.deploy(customSepolia, { sponsored: true })`
4. `publicClient.readContract(HCAFactory.getAccountOwner)`
5. If owner is zero: submit `HCAFactory.setAccountOwner(smartAccountAddress, eoaAddress)`

### Code path

- Account init: `apps/manager/src/lib/smart-account/rhinestone.ts`
- HCA tx build: `apps/manager/src/lib/smart-account/hca-registry.ts`
- Transport routing: `packages/transaction-manager/src/machines/transaction.machine.ts`
- Intent submit:
  - `packages/transaction-manager/src/actors/warp-transport.actor.ts`
  - `packages/transaction-manager/src/actors/rhinestone-transport.actor.ts`

### Failing operation

- Contract: `ENS_SEPOLIA_CONTRACTS.HCAFactory`
- Function: `setAccountOwner(smartAccountAddress, eoaAddress)`
- Same-chain sponsored intent on `customSepolia`

### Observed error

Bundle simulation fails during the HCA registration intent.

Observed revert path:

- `IntentExecutor._checkSigAndExecute`
- `TheCompact.mustHaveARegisteredAllocator`

### Notes

- This is the post-connect HCA registration step, not a read call.
- Token balances still load because those are read-only RPC calls and do not depend on this tx succeeding.

## Issue 2: Enable Smart Sessions Fails During Signature Step

### Current status

To isolate session behavior, HCA registration was temporarily bypassed with:

```bash
VITE_FF_DISABLE_HCA_REGISTRATION=true
```

This allows the app to get past HCA registration and reach the Smart Sessions flow.

### Sequence when clicking "Enable Smart Sessions"

1. `experimental_getSessionDetails([sdkSession])`
2. `experimental_signEnableSession(sessionDetails)` <- failing here
3. `experimental_enableSession(...)`
4. `rhinestoneAccount.sendTransaction(...)`
5. `rhinestoneAccount.waitForExecution(...)`

### Code path

- Session creation: `apps/manager/src/lib/smart-account/sessions/rhinestone-session.ts`

### Observed error

The failure happens before the on-chain enable tx, during the typed-data signature request:

```text
Failed to create Rhinestone session: An internal error was received.
Details: Keyring Controller signTypedMessage: ParserError:
Unable to encode value:
Number "115792089237316195423570985008687907853269984665640564039457584007913129639936"
is out of range for type "uint256".
Version: viem@2.41.2
```

### Notes

- This is the same MetaMask EIP-712 sign popup generated by `experimental_signEnableSession(...)`.
- It is not yet the on-chain session enable transaction.
- We added a 7-day session timeframe in the app to avoid an implicit "unlimited" session bound, but the same typed-data error still occurs.

## Additional Notes

- External MetaMask EOA path fails.
- Para embedded wallet path does not show the same failures.
- This suggests either:
  - a signer-path difference between external and embedded wallets, or
  - an account-state difference between those two owners.

## Current Questions

1. Why does the external EOA HCA registration intent fail with allocator registration revert while the embedded wallet path succeeds?
2. Why does `experimental_signEnableSession(...)` produce typed data containing a `uint256` value equal to `2^256`, which MetaMask/viem rejects as out of range?
3. Is there any required account/session onboarding step for external EOA-owned Rhinestone accounts before:
   - first HCA registration intent
   - first smart-session enable signature
