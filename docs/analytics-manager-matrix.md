# Manager analytics event matrix (WEB-1251)

Implemented source-grounded contract; see [shared handoff](analytics.md) for validation and deployment setup. All events require opt-in; no names, record values, wallet addresses or errors in new properties. Shared metadata comes from the adapter. Flow identifiers are opaque UUIDs; an identity/consent change suppresses later events from the old flow.

## Implemented triggers and manual QA

The rows above are implemented except dedicated Manager subname creation: no new subname UI was added. HCA execution is identified on registration/renewal starts by `execution_method`; it is not the connected wallet identity. Notification preference writes additionally emit `notifications:preferences_update` after a successful parsed API response. DNS and advanced resolver workflows are covered by Explorer's matrix. No terminal `flow_fail` is emitted for recoverable attempt errors or navigation away.

Registration child milestones are mapped by the pure `registrationAnalyticsStep.ts`: resolver setup → `setup`, funding permit or token approval → `approval`, commit → `commit`, wait → `cooldown`, reveal → `registration`, confirmation verification → `verification`. Background pricing/budget reads do not generate steps. Consecutive snapshots within the same milestone are suppressed by a single last-observed milestone in machine context. A retried milestone can appear again, as a new observed attempt. Optional setup emits one `post_registration` stage entry and, if it fails, a `stage_fail` for that step after the successful required registration.

Verification status: automated checks are recorded in the engineering handoff. These manual workflows are **not claimed browser-verified** by this matrix. Reload creates a fresh observed flow ID; recovered registration uses `flow_resume` rather than fabricating `flow_start`. No persisted analytics journal or cross-reload funnel stitching was introduced. Query observed completion with flow IDs; use wallet identity for consenting cross-app analysis, not a presumed Manager→Explorer funnel.

## Design notes

The registration machine already has monotonic progress, nullable setup fields and several retry/recovery branches. This change keeps only the last observed analytics milestone for deduplication and leaves transaction decisions intact. A future state-union cleanup should preserve the existing machine tests and optional setup behavior; it is not part of this instrumentation change. Bulk renewal retains its existing run guard and completed-name set instead of adding another operation journal.


Visible surfaces: the three Manager providers subscribe to idle pricing/select snapshots after SDK initialization, consent and wallet identity effects settle. They observe only the currently visible screen: persisted-consent reload emits one flow view and its current screen; granting consent on payment emits payment without replaying duration. Consecutive identical snapshots add no views, while returning to a pricing screen observes it again. Active execution snapshots are excluded. Operation starts/resumes bind their capture to the initiating wallet and consent epoch; later SDK readiness never rebinds that operation. Payment choices use live capture, with `payment_asset` and optional `funding_chain_id` (absent for the wallet). The machines contain no SDK-readiness events or identity keys.
