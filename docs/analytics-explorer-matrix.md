# Explorer analytics implementation matrix (WEB-1251)

All custom events require analytics consent. Names, wallet addresses, transaction hashes and record contents are excluded from product payloads. `source_app=explorer` distinguishes equivalent outcomes from Manager. An operation captures its initiating analytics identity and does not emit after an identity change.

| Flow | Actual source and milestones | Events / properties | Outcome semantics and QA |
| --- | --- | --- | --- |
| Registration | `useRegistrationTransactions`: explicit START/RESUME; shared registration actor's grouped setup, commit, cooldown, approval, register and verification stages | `registration:flow_start`, `registration:flow_resume`, `registration:stage_enter`, `registration:stage_fail`, `registration:flow_complete`; `flow_id`, `execution_method=eoa`, `stage`, `chain_id` | Confirmed reveal receipts or bounded read-only verification establish completion. A queued-submit callback attaches observation before UI publication; global manager cleanup triggers verification without continuing paid work. Recoverable machine `error` is step failure, never terminal flow failure. Retry retains flow. QA: commit rejection, approval rejection, cooldown, reveal confirmation, resume, wallet switch. |
| Records | `saveRecords`: prepare, submit, `waitForTransaction` | `profile:records_update`; `chain_id`, `record_count` | Receipt-confirmed write, never mutation submission. QA: failed receipt emits no outcome; switch wallet while awaiting receipt. |
| Primary name | `setReverseResolution`: submit, `waitForTransaction` | `profile:primary_name_update`; `chain_id` | Confirmed reverse-name write; forward-record write alone is not primary-name completion. QA: reject then retry; L1/L2. |
| Subname | `createSubname`: submit, `waitForTransaction` | `subname:name_create`; `chain_id` | Confirmed contract creation. QA: v1/v2, reject, repeat callbacks, switch wallet. |

| Search | `HomeSearchInput` explicit result navigation | `name_search:result_select`; `result_type` (`name`, `address`, `resolver`), `is_available=true` for registration links | User selection only, no debounced keystroke events. QA popover, keyboard, modal, owned/available/address/resolver. |
| Renewal | `useRenewalTransactions`: explicit single/bulk start; actual submission and `observeTransactionReceipt` | `renewal:flow_start`, `renewal:stage_enter`, `renewal:stage_fail`, `renewal:transaction_confirm`, `renewal:flow_complete`; `flow_id`, `chain_id`, final `item_count` | Each successful receipt produces confirmation; final completion requires every required transaction. Known submitted hashes/bundle IDs survive hard cleanup using the shared read-only receipt actor. Done/unmount do not determine success; cleanup and RPC timeout alone are not execution failure. Use counts of outcomes for feature adoption; registration funnel breaks down stages by source app and execution method. Cooldown entry means the actual waiting state, not a preliminary age lookup. Compare flow-level conversion using distinct `flow_id`, not number of stage events. Browser QA and PostHog ingestion remain separate checks.

## Manual QA, in risk order

Use a staging project and Sepolia-funded disposable wallets A/B. Filter live events by `source_app=explorer`; inspect properties and distinct ID. No synthetic traffic may target production. These are expected sequences, **not claims of browser verification**.

1. **Switch wallet during an operation:** accept analytics, connect A, start any write, switch to B before receipt. The delayed A outcome must not appear under B. Repeat with disconnect, consent withdrawal/regrant, and a second app tab withdrawing consent. No pre-consent events may replay later. Shared identity/consent QA is owned by the integration handoff.
2. **Registration:** open `/register?name=<available-test-name>`, choose duration/payment, start setup. Expect `flow_start`, then grouped `stage_enter(stage=...)` values for setup/commit/cooldown/approval/registration/verification as applicable; consecutive states inside a group produce one view. Moving to another group never implies stage success. Reject commit or approval: expect `stage_fail(stage=...,is_retryable=true)` and **no flow_complete**. Retry: `flow_retry`, stage entry, then subsequent progress under the same `flow_id`. Only confirmed/verified final success produces one `flow_complete`. Leave the screen while reveal submission is pending and after submission; verified completion must not require a mounted registration UI. Check dedicated-resolver reuse, atomic setup and separate approval paths. Reload recovery emits `flow_resume` with a new correlation segment, not a replay of the old start/steps. Completed persistence is deleted by existing registration logic; verify repeated reload does not complete it again.
3. **Renewal:** extend one name, then a mixed v1/v2 selection using the bulk extension UI. Expect `flow_start`, `stage_enter(stage=execution)` on wallet action, one `transaction_confirm(stage=approval|execution)` for each successful receipt, and final `flow_complete(item_count=<selected names>)` after all stages. Fail partway: successful stages remain, final completion must be absent. Navigate away before confirmation without clicking Done; expect completion once. Repeated callbacks must not duplicate confirmations/completion. Approval successes are transaction stages, not renewed items. Per-item verified expiry counts remain unimplemented; a failed attempt emits `stage_fail`, and a later attempt emits `flow_retry`.
4. **Records, primary name, subname:** edit records on a name, set reverse primary name, and create subnames on v1/v2. Each confirmed write emits its dedicated event once, with `chain_id` and (records only) `record_count`. Wallet rejection/failed receipt must emit no business outcome. Values, names, addresses and hashes must be absent. Primary-name event means confirmed reverse-name update; independently verify forward resolution in the UI.
5. **Explorer advanced tools:** change resolver, link/unlink records, grant/revoke resolver roles, grant/revoke registry roles. Expect `resolver:configuration_update` with action `change/link/unlink/roles_grant/roles_revoke`, or `roles:permissions_update` with action `grant/revoke`, only after confirmed receipt. Reject requests to prove no false outcome. Sync a DNS manager: `dns:manager_sync` after confirmation, no proof data. Click migration upgrade: `migration:manager_open(is_wrapped=...)`, never migration completion in Explorer.
6. **Search:** use popover keyboard and mouse selections and the search modal for names, available registrations, addresses and resolvers. Expect one `name_search:result_select(source=search,result_type=...)` per destination navigation, no event on keystrokes/debounce and no raw query/name/address.

## Verification evidence and limits

Current checks, test-pruning decisions and browser observations are in [the shared handoff](analytics.md). Retained real-actor and hook tests cover grouping, failure/retry correlation, verified completion, partial progress, cleanup and replacement actors. Mutation checks prove that accepting unverified registration or dropping actor-identity guards fails those tests. Pre-feature cases and assertions remain unchanged.

- Real-wallet browser workflows and staging ingestion still require manual QA.
- Deferred: DNS import step instrumentation, per-item bulk renewal verified expiry counts, registry deployment/parent configuration, transfer/fuse operations and notifications. DNS debugger events retain controlled source and verdict categories without name or failed-step labels.

## Query use

Use ordered registration funnels by `flow_id`: flow start/resume → commit → cooldown → registration → flow complete, with applicable setup/approval branches as optional steps. Compare `source_app` rather than treating apps as funnel stages. Renewal funnel: start → execution → complete. Use `stage_fail` for registration friction; renewal transaction confirmations measure completed transaction stages and must not be counted as renewed names. Sum final renewal `item_count` for completed batches only. Feature adoption uses dedicated management outcomes grouped by app/chain/action. Migration handoff is adoption of the upgrade link, not a migration success rate.

## Entry funnels and protocol dimensions

Registration now observes the available-name duration form before execution. Payment visibility is a separate observation when the connected-wallet payment controls are shown, even though both controls share one page. The observed entry ID is retained into the accepted start and existing actor-owned outcomes. A resumed operation keeps its existing separate correlation segment; earlier screens are not replayed.

Renewal entry observes the open modal, duration/settings surface and payment confirmation/summary. Single/multi-name starters retain that ID into receipt-backed execution. Every renewal event carries protocol context derived from the actual selected name targets: `v1`, `v2` or `mixed`; bulk events additionally carry `v1_item_count` and `v2_item_count`. Those are selection counts, not an assertion about per-name confirmed expiry.

1. Open registration without a wallet, consent accepted: `registration:flow_view`, `duration_view`. Connect: one `payment_view`. Starting execution must retain `flow_id`; no separate page transition is inferred between controls on the same page.
2. Open single renewal; observe entry, then duration/settings, then payment confirmation. Expect `renewal:flow_view`, `duration_view`, `payment_view`, followed by the same flow's existing start/stages/outcome. Non-owner disclaimer entry may precede duration.
3. Repeat with a mixed V1/V2 bulk selection. Compare version counts to actual names and verify `protocol_version=mixed` on entry, start, receipt confirmations and completion. Reject/retry partway without a premature completion.
4. Deny consent on entry, grant on confirmation: observe only the currently visible screen, no historical duration visit. Re-renders do not add views; returning to a screen may.
5. On `/alice.eth/edit-records` (replace with a controlled test name), observe the editor, make one actual addition/change/deletion, then save: `profile:edit_view`, `edit_start`, `save_start`, confirmed `records_update`, `save_complete(save_type=records)` with the same `flow_id`. Reject and retry: a failed attempt remains distinct from final success.
6. Cold-load the editor with saved consent, discard/re-edit, leave while awaiting a receipt and switch wallet while pending. Compare capture to the visible state; no raw values, false success or outcomes attributed to the new wallet.

Views are best-effort current-surface observations after consent/identity readiness. Outcomes remain service/actor-owned. All sequences above still require real-wallet browser QA; unit/hook tests do not establish ingestion. Remaining coverage and revenue setup are in `analytics.md`.
