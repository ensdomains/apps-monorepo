# Explorer analytics implementation matrix (WEB-1251)

All custom events require analytics consent. Names, wallet addresses, transaction hashes and record contents are excluded from product payloads. `source_app=explorer` distinguishes equivalent outcomes from Manager. An operation captures its initiating analytics identity and does not emit after an identity change.

| Flow | Actual source and milestones | Events / properties | Outcome semantics and QA |
| --- | --- | --- | --- |
| Registration | `useRegistrationTransactions`: explicit START/RESUME; shared registration actor's grouped setup, commit, cooldown, approval, register and verification stages | `registration:flow_start`, `registration:flow_resume`, `registration:step_view`, `registration:step_result`, `registration:flow_complete`; `flow_id`, `registration_method=eoa`, `step`, `chain_id` | Only actor `success` after registration verification completes. Recoverable machine `error` is step failure, never terminal flow failure. Retry retains flow. QA: commit rejection, approval rejection, cooldown, reveal confirmation, resume, wallet switch. |
| Records | `saveRecords`: prepare, submit, `waitForTransaction` | `profile:records_update`; `chain_id`, `record_count` | Receipt-confirmed write, never mutation submission. QA: failed receipt emits no outcome; switch wallet while awaiting receipt. |
| Primary name | `setReverseResolution`: submit, `waitForTransaction` | `profile:primary_name_update`; `chain_id` | Confirmed reverse-name write; forward-record write alone is not primary-name completion. QA: reject then retry; L1/L2. |
| Subname | `createSubname`: submit, `waitForTransaction` | `subname:name_create`; `chain_id` | Confirmed contract creation. QA: v1/v2, reject, repeat callbacks, switch wallet. |
| Resolver / role administration | resolver `changeResolver`, `linkRecords`, role grant/revoke helpers wait for confirmation | `resolver:configuration_update`, `roles:permissions_update`; `chain_id`, controlled `action` | Successful receipt only. No resolver addresses, role masks, target names. QA each action and failed receipt. |
| Search | `HomeSearchInput` explicit result navigation | `name_search:result_select`; `result_type` | User selection only, no debounced keystroke events. QA popover, keyboard, modal, owned/available/address/resolver. |
| Renewal | `useRenewalTransactions`: explicit single/bulk start; decorated modal transaction callbacks | `renewal:flow_start`, `renewal:step_view` (`review`, `execution`), `renewal:step_result`, `renewal:flow_complete`; `flow_id`, `chain_id`, final `item_count` | Step results require successful receipt callbacks; final completion requires every current step callback and deduplicates repeats. Interrupted batches retain successful step results without a final completion. No inferred per-item partial count. QA single, atomic, mixed v1/v2 partial batch. |
| Migration handoff | `UpgradeActions` links to Manager | `migration:manager_open`; `is_wrapped` | Click intent only; Manager owns actual migration execution and completion. |
| DNS manager sync | `useSyncManagerTransaction.runSync` after `waitForTransaction` | `dns:manager_sync`; `chain_id` | Confirmed write only, no raw proof or name. |
| HCA / DNS import | Existing specialized UI | No additional completion events | Explorer registration uses the EOA signer path; no HCA-specific flow is invented. DNS import intermediate events remain follow-up. DNS debugger events remain separate diagnostics. |

Use counts of outcomes for feature adoption; registration funnel breaks down steps by source app and execution method. Compare flow-level conversion using distinct `flow_id`, not number of step events. Browser QA and PostHog ingestion remain separate checks.

## Manual QA, in risk order

Use a staging project and Sepolia-funded disposable wallets A/B. Filter live events by `source_app=explorer`; inspect properties and distinct ID. No synthetic traffic may target production. These are expected sequences, **not claims of browser verification**.

1. **Switch wallet during an operation:** accept analytics, connect A, start any write, switch to B before receipt. The delayed A outcome must not appear under B. Repeat with disconnect, consent withdrawal/regrant, and a second app tab withdrawing consent. No pre-consent events may replay later. Shared identity/consent QA is owned by the integration handoff.
2. **Registration:** open `/register?name=<available-test-name>`, choose duration/payment, start setup. Expect `flow_start`, then grouped `step_view` values for setup/commit/cooldown/approval/registration/verification as applicable; consecutive states inside a group produce one view. Advancing to another group produces `step_result(outcome=success)` for the previous stage. Reject commit or approval: expect `step_result(outcome=failure,is_retryable=true)` and **no flow_complete**. Retry: `flow_retry`, step view, then subsequent progress under the same `flow_id`. Only verified final success produces one `flow_complete(item_count=1)`. Check dedicated-resolver reuse, atomic setup and separate approval paths. Reload recovery emits `flow_resume` with a new correlation segment, not a replay of the old start/steps. Completed persistence is deleted by existing registration logic; verify repeated reload does not complete it again.
3. **Renewal:** extend one name, then a mixed v1/v2 selection using the bulk extension UI. Expect `flow_start`, `step_view(review)`, `step_view(execution)` on wallet action, one `step_result(success)` for each confirmed transaction stage, and final `flow_complete(item_count=<selected names>)` after all stages. Fail partway: successful stages remain, final completion must be absent. Repeated modal callbacks must not duplicate success results/completion. Approval successes are transaction stages, not renewed items. Per-item partial counts and failure/retry step events remain unimplemented.
4. **Records, primary name, subname:** edit records on a name, set reverse primary name, and create subnames on v1/v2. Each confirmed write emits its dedicated event once, with `chain_id` and (records only) `record_count`. Wallet rejection/failed receipt must emit no business outcome. Values, names, addresses and hashes must be absent. Primary-name event means confirmed reverse-name update; independently verify forward resolution in the UI.
5. **Explorer advanced tools:** change resolver, link/unlink records, grant/revoke resolver roles, grant/revoke registry roles. Expect `resolver:configuration_update` with action `change/link/unlink/roles_grant/roles_revoke`, or `roles:permissions_update` with action `grant/revoke`, only after confirmed receipt. Reject requests to prove no false outcome. Sync a DNS manager: `dns:manager_sync` after confirmation, no proof data. Click migration upgrade: `migration:manager_open(is_wrapped=...)`, never migration completion in Explorer.
6. **Search:** use popover keyboard and mouse selections and the search modal for names, available registrations, addresses and resolvers. Expect one `name_search:result_select(source=search,result_type=...)` per destination navigation, no event on keystrokes/debounce and no raw query/name/address.

## Verification evidence and limits

- Portal `pnpm typecheck` passed after implementation.
- Targeted registration/renewal analytics tests cover grouping, failure→retry correlation, verified completion, partial progress and callback deduplication. Both new sequence tests were deliberately run against broken deduplication and failed; code was restored.
- Final affected test run: 7 files / 69 tests passed (registration observer/hook, renewal observer/hook, records helper, search input, migration banner). Earlier resolver/helper focused checks also passed. Existing RPC calls printed DNS failures in the sandbox and happy-dom printed a teardown AbortError; test command exited 0. No existing assertions were changed.
- Browser wallet workflows and staging ingestion were not performed by this workstream. Parent integration QA may add observations separately.
- Deferred: DNS import step instrumentation, per-item bulk renewal verified expiry counts, renewal step failure/retry events, registry deployment/parent configuration, transfer/fuse operations and notifications. Existing DNS debugger events retain their diagnostic semantics; the shared adapter sanitizes payloads.

## Query use

Use ordered registration funnels by `flow_id`: flow start/resume → commit → cooldown → registration → flow complete, with applicable setup/approval branches as optional steps. Compare `source_app` rather than treating apps as funnel stages. Renewal funnel: start → execution → complete. Use `step_result` failures for registration friction; renewal success results measure completed transaction stages and must not be counted as renewed names. Sum final renewal `item_count` for completed batches only. Feature adoption uses dedicated management outcomes grouped by app/chain/action. Migration handoff is adoption of the upgrade link, not a migration success rate.
